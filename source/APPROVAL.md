# Approve a tested candidate

Build success does not establish hardware safety. The approval workflow records
a maintainer's explicit test attestation for one exact candidate and specified
physical models. CI validates the report and package hashes. CI does not perform
the hardware tests or independently verify the report's claims.

**Current rollout hold:** the replacement installer is wired, but target
end-to-end installation and hardware tests remain unfinished. No candidate
currently has the evidence needed for approval.
Do not submit a passing report until those tests actually pass.

## Required evidence

Use a spare supported UGREEN system with local console access and recoverable
boot media. Do not use a production server for the first driver activation.
Retain the previous plugin, settings, and packages for recovery. The existing
network-loss report has not been diagnosed or proven fixed.

Record the following results for each exact system product name:

- New installation and migration from the legacy plugin both succeed.
- Existing disk mappings and settings remain unchanged.
- A reboot restores the intended plugin operation without network loss.
- Rollback restores the previous installation and settings.
- Disk LEDs and network LEDs show the original monitor's supported behavior.
- Network interfaces and connectivity remain available during activation,
  activity, monitor restart, and reboot.

The original DXP480T monitor provides static LEDs, not disk/network activity.
For that model, record `not-applicable-static-model` for both activity checks
and add `"static_leds": "pass"` to its result. Network connectivity still
requires a passing result. Do not generalize one model's result to other models.

## Submit the report

1. Download the candidate from its exact kernel release, such as `6.18.47-Unraid`.
2. Compute the SHA-256 of its `unraid-<version>-r1.json` receipt.
3. Complete the required tests against the packages named in that receipt.
4. Publish a redacted report in this repository's issues.
5. Include test steps, observed results, package identity, and recovery evidence.
6. Remove credentials, serial numbers, addresses, and unrelated diagnostic data.
7. Run **Approve tested UGREEN candidate** from `master` with the report JSON.

Use this structure, replacing every placeholder with actual evidence. The
example intentionally fails validation and must not be submitted unchanged.

```json
{
  "unraid": "7.4.0-beta.2",
  "kernel": "6.18.47-Unraid",
  "manifest_sha256": "REPLACE_WITH_RECEIPT_SHA256",
  "confirm_hardware_tested": false,
  "evidence_url": "REPLACE_WITH_REPOSITORY_ISSUE_URL",
  "results": [
    {
      "system_product_name": "REPLACE_WITH_EXACT_DMI_PRODUCT_NAME",
      "checks": {
        "new_install": "untested",
        "legacy_upgrade": "untested",
        "settings_preserved": "untested",
        "reboot": "untested",
        "rollback": "untested",
        "disk_leds": "untested",
        "network_leds": "untested",
        "network_connectivity": "untested"
      }
    }
  ]
}
```

Only completed passing checks permit `confirm_hardware_tested: true`. A failed
or missing check blocks approval. The workflow verifies that the evidence issue
exists, not that its contents prove the attestation. The maintainer must review
that evidence before dispatch. Repository workflow permissions control who can
dispatch. There is no additional environment-review gate configured here.

## Publication and recovery

The workflow uploads `approved-unraid-<version>-r1.json` under the existing
kernel tag, then removes the release's prerelease flag. The approval binds the
receipt hash, OS, kernel, exact models, evidence URL, approver, and time.

Other OS/model combinations within that kernel release remain unapproved.
The eventual installer must require the exact approval receipt and model match.
The release's prerelease flag alone is not an installation authorization.

An identical retry retains the original approval and resumes the release edit.
A different attestation cannot overwrite it. A conflict requires investigation,
not deletion or `--clobber`. Changed packages require a reviewed recipe revision
and new test evidence. No real approval is generated by the unit tests.
